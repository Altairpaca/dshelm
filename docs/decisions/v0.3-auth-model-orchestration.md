## 1. Product objective

DSHelm is an OmO-inspired, DSH-native agent distribution. Its product value is
the composition of resources a user already owns: accounts, subscriptions,
API keys, local models, DSH plugins, and external product runtimes. The default
journey is:

```text
npx dshelm init
  -> discover DSH, resources, auth readiness, and capabilities
  -> recommend a topology from current evidence
  -> install a usable profile
  -> explain and verify each execution decision
```

The router does not assign permanent identities such as "Claude reviewer" or
"DeepSeek worker". It resolves task requirements against available resources,
hard constraints, evidence-backed preferences, and user policy.

## 3. Verified auth facts

The DSH rc.7 pi-ai adapter constructs `createModels()` with no options, so it
uses pi-ai's `InMemoryCredentialStore`. The adapter resolves a named DSH
credential through `ctx.credentials` and passes the resulting API key as a
request override. It does not inject a pi-ai `CredentialStore`, call
`Models.login()`, or expose provider-owned login/logout interaction.

The pi-ai v0.82.1 public seam is provider-neutral and reusable:

- `Provider.auth` declares `apiKey` and/or `oauth` ownership.
- `Models.checkAuth`, `getAuth`, `login`, and `logout` provide status and
  provider-owned operations.
- `CredentialStore` has `read`, metadata-only `list`, serialized `modify`, and
  `delete`; refresh runs inside `modify` to avoid concurrent double refresh.
- `OAuthAuth.login`, `refresh`, and `toAuth` own flow and token translation.
- `AuthInteraction` supports interactive prompts, browser URLs, device codes,
  progress, cancellation, and headless-capable implementations.
- A stored credential is one type-tagged credential per provider. A stored
  credential owns that provider; a failed refresh never silently falls back to
  an environment key.

The DSH note
`.agents/notes/implemented/bug-fix/2026-08-13-oauth-only-providers-withheld.md`
therefore remains correct: OAuth-only catalog routes are withheld by the DSH
settings directory because the adapter has no persistent store or login
surface. This is a missing integration seam, not evidence that pi-ai lacks one.

The first DSHelm bridge now uses that public seam without reading another
product's credential files. `FileCredentialStore` implements pi-ai's
`CredentialStore` with a Zod-validated versioned document, a `0600` file,
`0700` parent directory, atomic temporary-file rename, and process-serialized
per-provider `modify`/`delete`. `createPiAiOAuthDriver` maps
`Models.checkAuth/login/logout` to the provider-neutral adapter and drops the
returned credential before it reaches Core. The current fallback is a secure
file; an OS-keychain backend remains an explicit follow-up seam, so this bridge
does not claim keychain-at-rest protection yet.

## 4. Auth/account contract

DSHelm will expose a provider-neutral auth layer. Core receives opaque
`CredentialRef` values and account status, never secret strings. Adapters are
classified by ownership:

| Adapter kind | Secret owner | DSHelm responsibility |
|---|---|---|
| `native-product-auth` | Product CLI/SDK/keychain | Probe install/login/status, request explicit login/logout, launch product runtime, report opaque handle |
| `library-oauth` | Provider-owned implementation plus DSHelm-injected persistent store | Run supported `login/checkAuth/logout`, serialize refresh, report credential lifetime and source |
| `api-key` | Host env/keychain or DSHelm credential store when explicitly configured | Probe reference, redact status, pass only an opaque reference to execution |
| `device-code` | Provider-owned device flow and its store | Show device instructions, poll with cancellation, never copy another product's private token |
| `gateway` | Enterprise gateway or host secret manager | Probe endpoint and auth reference; gateway policy remains outside Core |

The status vocabulary is `available`, `authenticated`, `expired`,
`action-required`, `unsupported`, and `unknown`. Every status names the auth
owner and evidence source. DSHelm never reads or copies private credential files
such as `~/.codex/auth.json`, Claude private stores, or xAI product stores.

## 5. Model knowledge contract

Model knowledge is a versioned, machine-readable evidence registry, not an
unattributed ranking file. Every claim carries source, observed time, model or
pattern, confidence, expiry/staleness policy, claim type, and optional URL or
commit. The four evidence classes are:

1. `runtime`: exact DSH `resolveModelInfo`, provider discovery, auth/runtime probe;
2. `official`: vendor documentation or API metadata for hard capability;
3. `community`: durable issues, discussions, harness reports, and benchmarks;
4. `empirical`: reproducible DSHelm evals with harness, prompt, tools, and date.

Hard capabilities include identity, protocol, context/output limits, reasoning
vocabulary, tools, structured output, vision, streaming, caching, availability,
license, local deployment, rate limits, price, and auth methods. Soft capabilities
include planning, coding, debugging, review, research, long-horizon stability,
tool-call reliability, and fan-out suitability. Soft claims cannot override a
runtime capability failure.

Knowledge refresh may use a signed/versioned data bundle and a local empirical
overlay. Remote bundles contain data only, never executable code. User overrides
can change soft preferences but cannot manufacture runtime capability.

## 6. Routing and trace contract

The route input is `TaskRequirements`, not a permanent role-to-model table.
Requirements may include planning strength, long-horizon coding, cheap
parallelism, vision, independent verification, large context, latency, local
only, structured output, cost, auth, and harness constraints.

Resolution filters hard constraints first, scores evidence-backed soft claims,
then applies explicit user policy. The result records candidates, rejections,
auth readiness, model knowledge snapshot, provider/model/reasoning, backend,
harness/product runtime, context inheritance, durability, tools, fallback, and
the evidence behind the final choice.

DSH-native requests must be checked against the actual request/header or
adapter options. Product-managed runtimes are explicitly marked
`PRODUCT_MANAGED` when their final model cannot be observed. Configuration
prediction is never execution evidence.

branch. Stage 1 starts with a keyless auth registry and model knowledge schema,

  vocabulary, native-product, provider-owned OAuth, and host API-key adapters;
