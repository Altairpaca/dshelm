## 1. 产品目标

DSHelm 是受 OmO 启发、原生 DSH、面向生态组合的 agent distribution。产品
价值在于组织用户已经拥有的资源：账户、订阅、API key、本地模型、DSH 插件和
外部产品运行时。默认路径是：

```text
npx dshelm init
  -> 发现 DSH、资源、认证状态和能力
  -> 根据当前证据推荐 topology
  -> 安装可用 profile
  -> 解释并验证每次执行决策
```

路由器不为模型永久分配「Claude reviewer」或「DeepSeek worker」这类身份，而是
根据任务需求、硬约束、有证据的偏好和用户 policy 解析资源。

## 3. 已验证的认证事实

DSH rc.7 的 pi-ai adapter 用无参数 `createModels()` 构造 models，因此使用的是
pi-ai 的 `InMemoryCredentialStore`。adapter 通过 `ctx.credentials` 解析具名 DSH
credential，并将结果作为 request override 传给 API。它没有注入 pi-ai
`CredentialStore`，没有调用 `Models.login()`，也没有暴露 provider 自己的
login/logout 交互。

pi-ai v0.82.1 的公共 seam 已经是 provider-neutral 且可复用的：

- `Provider.auth` 声明 `apiKey` 和/或 `oauth` 的所有权。
- `Models.checkAuth`、`getAuth`、`login`、`logout` 提供状态和 provider-owned 操作。
- `CredentialStore` 只有 `read`、只返回元数据的 `list`、串行化 `modify` 和
  `delete`；刷新在 `modify` 锁内执行，避免并发重复刷新。
- `OAuthAuth.login`、`refresh`、`toAuth` 负责流程和 token 转换。
- `AuthInteraction` 支持交互 prompt、浏览器 URL、device code、进度和取消，
  也可承载 headless 实现。
- 每个 provider 一个带类型的 credential。已存 credential 拥有该 provider；
  刷新失败时绝不会静默退回环境 key。

DSH 的 `.agents/notes/implemented/bug-fix/2026-08-13-oauth-only-providers-withheld.md`
因此仍然成立：settings directory 会隐藏仅 OAuth 的 catalog route，因为 adapter
没有持久 store 或 login surface。这是缺少集成 seam，不是 pi-ai 缺少 seam。

第一条 DSHelm bridge 已复用这个公开 seam，但不会读取其他产品的 credential 文件。
`FileCredentialStore` 实现 pi-ai 的 `CredentialStore`：使用 Zod 校验的版本化文档、
`0600` 文件、`0700` 父目录、临时文件原子 rename，以及按 provider 串行化
`modify`/`delete`。`createPiAiOAuthDriver` 将 `Models.checkAuth/login/logout` 映射到
provider-neutral adapter，并在 credential 返回 Core 前丢弃它。当前 fallback 是安全文件；
OS keychain backend 仍是明确的后续 seam，因此当前 bridge 不宣称 keychain-at-rest 保护。

## 4. Auth/account 契约

DSHelm 将提供 provider-neutral auth layer。Core 只接收不透明的 `CredentialRef`
和账户状态，绝不接收 secret 字符串。adapter 按所有权分类：

| Adapter 类型 | Secret 所有者 | DSHelm 责任 |
|---|---|---|
| `native-product-auth` | 产品 CLI/SDK/keychain | 探测安装、登录、状态；请求显式 login/logout；启动产品运行时；报告不透明 handle |
| `library-oauth` | provider-owned 实现与 DSHelm 注入的持久 store | 运行受支持的 `login/checkAuth/logout`；串行刷新；报告生命周期与来源 |
| `api-key` | 主机 env/keychain，或用户明确配置的 DSHelm store | 探测引用、输出脱敏状态，只把不透明引用传给执行层 |
| `device-code` | provider-owned device flow 与其 store | 展示设备说明、可取消轮询，绝不复制其他产品私有 token |
| `gateway` | 企业 gateway 或主机 secret manager | 探测 endpoint 和 auth 引用；gateway policy 保持在 Core 之外 |

状态词汇为 `available`、`authenticated`、`expired`、`action-required`、
`unsupported`、`unknown`。每个状态都写明 auth owner 和证据来源。DSHelm 绝不读取
或复制 `~/.codex/auth.json`、Claude 私有 store 或 xAI 产品私有 store。

## 5. Model knowledge 契约

模型知识是带版本的机器可读 evidence registry，不是没有来源的排名文件。每条
claim 都带 source、观察时间、model/pattern、confidence、过期/陈旧策略、claim
type，以及可选 URL 或 commit。四类证据是：

1. `runtime`：精确 DSH `resolveModelInfo`、provider discovery、auth/runtime probe；
2. `official`：厂商文档或 API metadata，用于硬能力；
3. `community`：长期 issues、讨论、harness 报告和 benchmark；
4. `empirical`：带 harness、prompt、工具和日期的可复现实验。

硬能力包括 identity、protocol、上下文/输出上限、reasoning 词汇、工具、结构化
输出、视觉、多模态、streaming、缓存、可用性、license、本地部署、限流、价格和
认证方法。软能力包括规划、编码、debug、review、research、长程稳定性、工具调用
可靠性和 fan-out 适应性。软 claim 不能覆盖 runtime capability failure。

刷新可以使用签名/版本化 data bundle 和本地 empirical overlay。远端 bundle 只能
包含数据，不能包含可执行代码。用户 override 可以改变软偏好，但不能伪造 runtime
capability。

## 6. 路由与 trace 契约

路由输入是 `TaskRequirements`，不是永久的 role-to-model 表。需求可以包括规划
强度、长程编码、廉价并行、视觉、独立验证、大上下文、延迟、本地-only、结构化
输出、成本、认证和 harness 约束。

解析先过滤硬约束，再使用有证据的软 claim 打分，最后应用显式用户 policy。结果
必须记录候选、拒绝原因、auth readiness、model knowledge snapshot、provider/model/
reasoning、backend、harness/product runtime、context inheritance、durability、工具、
fallback，以及最终选择所依据的证据。

DSH-native request 必须和真实 request/header 或 adapter options 对照。外部产品
运行时无法观察最终模型时必须明确标记 `PRODUCT_MANAGED`。配置预测不算执行证据。

## 7. 当前阶段与假设

Stage 0 在本契约从 feature branch 提交并推送后完成。Stage 1 从 keyless auth
registry 和 model knowledge schema 开始，并用至少以下内容证明 vertical slice：

- 一个 `native-product-auth` fixture 和一个 `library-oauth` fixture；
- 一个 API-key resource、一个 OAuth resource、一个 local/open resource；
- DSH-native 与 AgentTeams 执行元数据；
- 脱敏账户状态和确定性的 explain trace。

本分支已有的 Stage 1 证据：

- `@dshelm/auth` 提供不透明 `CredentialRef`、与所有权无关的状态词汇、
  native-product、provider-owned OAuth 和主机 API-key adapter；测试覆盖脱敏和
  显式 login/logout 委托。
- `@dshelm/model-knowledge` 提供 Zod 校验的纯数据 bundle，包含四类 evidence、
  陈旧状态、explain 输出和六条 baseline 记录。只来自 pi-ai 的非 DeepSeek baseline
  claim 明确标为 community evidence 并限制 confidence，不作为默认路由。
- CLI 已接入 `dshelm auth list|status|login|logout`、`dshelm models inspect|explain`、
  `dshelm knowledge status` 和 `dshelm init [--yes]`。`init` 写入发现
  profile 和 `.dshelm/dsh-profile/package.json`，不写 credential ref，可重复执行，
  也不会静默登录。
- `dshelm uninstall --yes` 默认只删除生成的 profile；`--purge-credentials` 是额外的
  显式破坏性选项。
- 默认 auth registry 会发现声明 provider-owned OAuth 的 pi-ai provider
  （`pi-ai/anthropic`、`pi-ai/openai-codex`、`pi-ai/xai` 等），并且只在
  DSHelm 自己管理的 credential 位于用户级 platform config 目录；

- 直接 DSH 依赖和 client package 已按公开 rc.7 构建；主机上的 `dsh --version` 仍是
  单独的环境探测。
- Core 的 `TaskRequirements` 现在支持认证/能力硬过滤和有证据的 soft score。Resolution
  Trace v2 记录候选 score、认证就绪、evidence、backend/harness、可观测性和 knowledge
  snapshot，同时不导入 model-knowledge 或任何厂商 SDK。DSH 暴露类型安全的纯数据
  knowledge overlay seam，并保留 exact runtime validity。

  和 typecheck 通过；

## 8. 测试与安全门

- 默认测试必须 keyless、hermetic、fixture-backed。
- OAuth 真登录只允许 opt-in manual E2E，不进入普通 CI。
- 在边界和 trace/log 中测试 credential redaction。
- `dshelm init` 绝不静默启动浏览器登录；login 必须是显式命令或显式交互步骤。
- 对 `api.deepseek.com` 的 credentialed 请求只能经过统一非高峰 gate，并报告
  `VERIFIED` 或 `SKIPPED: outside DSHelm live-test window`。
- clean temporary HOME journey 必须覆盖 install、init、discovery、profile 生成、
  doctor、explain 和 uninstall，用户无需手工编辑 package/Cordis 文件。
